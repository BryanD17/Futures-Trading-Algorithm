## 1. THE DEFECT (S5/S6)

On Main, G1 went through this sequence:

1. `SWEEP_DONE` at 14:45.
2. It waited for a NEW bearish displacement (the 15:00 bar).
3. `DISPLACED` at 15:10, then `MSS` at 15:15.
4. It waited for a SECOND retrace into the band.
5. It emitted at 15:26 (`e=30635.5`). The limit never filled.

In the OTE model the displacement and the MSS are the impulse leg that created the dealing range: HH 30759.25 in the 09:30 bar → LL 30356.75 in the 10:45 bar. The retrace into that range's OTE band, with a liquidity sweep and a PD-array rejection, is the entry. Main instead required a second displacement + MSS after the sweep, so it always arrived one leg late.

## 2. THE FIX — `ote.entryModel = IMPULSE_LEG | POST_SWEEP` (R3: corrected, never skipped)

The fix adds two EngineConfig keys:

- `ote.entryModel`: ENUM, default `IMPULSE_LEG`. `POST_SWEEP` is the pre-05.2 behaviour, kept for A/B.
- `ote.impulseLeg.minSweepFib`: DOUBLE, default `0.705`.

Both keys are in `engine-defaults.properties`, printed in the boot table's OTE line and in `OteConfig.describe()`, and read via `OteConfig` (no `System.getProperty`).

In IMPULSE_LEG mode, at step 10 (`SWEEP_DONE`), `OteSetupDriver.tryImpulseLegEntry` runs first. It applies only when every one of the conditions below holds:

| # | condition | G1 value |
|---|---|---|
| a | anchor = `DEALING_RANGE` and Agent 03's `ctx.rangeHigh/rangeLow` exist | 30759.25 / 30356.75 |
| b | sweep direction = bias (HIGH sweep for a short) | HIGH@30640.0 |
| c | swept LEVEL inside the band `[0.618, 0.786]` (premium for shorts / discount for longs, Agent 03 M2b semantics) | 30640.0 ∈ [30605.50, 30673.00] |
| d | the retrace's extreme since the episode's first sweep is also inside the band (a retrace that already traded beyond the 0.786 is not an OTE retrace) | 30650.00 ≤ 30673.00 |
| e | that extreme reaches `ote.impulseLeg.minSweepFib` (0.705 = the OTE sweet spot) | 30650.00 ≥ 30640.50 |
| f | no close beyond the range 1.0 | – |

If any condition fails, the verdict is recorded in `ctx.impulseLegVerdict` and **POST_SWEEP runs exactly as today**.

When the model applies, the mandatory gates are proven on the impulse leg with THE SAME detectors. The leg is located in `PdArrayLocator`'s 5m bars: for a short, the bar whose high = `rangeHigh` → the bar whose low = `rangeLow`.

- **M5.** At least one displacement of THE `DisplacementDetector` (same rule, same `displacement.atrMult` / `bodyPct`) in the bias direction on a leg bar. The detector now keeps `{atr, range/ATR, body}` per history entry (`DisplacementDetector.between(from,to,dir)`, `HISTORY_MAX` 50 → 200). There must also be a same-direction FVG created inside the leg: the displacement's own linked gap first, else the largest gap whose middle candle lies in the leg. It is recorded as `ctx.fvg` with `m5LinkKind = "IMPULSE_FVG"`.
- **M6.** An MSS event of THE MSS detector (`forStdvOte()`) on a leg bar at or after that displacement: the leg's close beyond the last opposing swing. The swing price and the breaking close are recorded. The driver's MSS buffer grew 50 → 200 events.
- **M7 ARM.** The zone is the dealing-range band, and the setup arms on this bar. The machine walks `SWEEP_DONE → DISPLACED → MSS_CONFIRMED → OTE_ARMED` in one candle through the existing core methods, and `OteArmedEvent` is published.
- **M7 ALARM** (`OteSetupDriver.alarm`, impulse branch). The PD array must reach the swept level:
  - **Candidates:**
    - the sweep's OB: the 5m bar CONTAINING the sweep, when it closed opposite to the trade and took the level (G1: the 14:50 bar [30621.00, 30650.00]);
    - the sweep bar's rejection WICK: the raid bar closed back through the level, with wick ≥ 50 % of range (G1: the 14:53 1m bar [30634.75, 30650.00], 77 %);
    - band-overlapping FVG / IFVG / BREAKER whose zone reaches the swept level.
  - **Reaction:** a candle in the band that CLOSES back beyond the swept level with a close in the trade direction (the rejection).
  - **Entry:** the PD-array edge (Agent 04's `bestInBand` / `entryLevel`).
  - **Stop:** beyond max(0.786, PD-array far edge, retrace extreme) + `stdvOte.stopBufferTicks`. G1: max(30673.00, 30650.00, 30650.00) + 4 ticks = **30674.00**, above the OB and above the owner's 30673.
  - **Targets:** T1 = 0.5 (30558.00), T2 = 0.382 (30510.25 → 30510.5 tick-rounded ladder), T3 = range low (30356.75), unchanged.
  - **Invalidate:** Agent 04's rule (CLOSE beyond the range 1.0) and window (`ote.windowBars`) are kept.
- **Validator** (`MandatoryConfluenceValidator`, M5/M6/M7 only). When `ctx.oteEntryModel == IMPULSE_LEG` it RE-CHECKS the recorded numbers:
  - M5: displacement on the leg, range/ATR ≥ atrMult, body ≥ bodyPct, FVG stamped inside the leg;
  - M6: close beyond the swing, on a leg bar;
  - M7: swept level inside the band;
  - Agent 04's existing checks (RR band, entry in band, MSS not before displacement) still apply.
- **CSV / transcript.** `FunnelAutopsyHarness` gains the columns `entryModel, impulseLeg, impDispRangeAtr, impDispBody, impMssSwing, impMssClose, impulseVerdict`. The transcript prints the verdict when it changes.

Why `minSweepFib = 0.705`: on G1 the same London-high liquidity was raided three times.

- **14:45:** Current Session High 30627.00, extreme 30627.75.
- **14:49:** Equal Highs 30636.13, extreme 30638.00.
- **14:53:** London High 30640.00, extreme 30650.00.

All three levels are inside the band. Only the 14:53 raid reached the OTE sweet spot 30640.50, and it is the one the owner sold. With 0.618 (any touch) the engine arms at 14:45 and alarms on the 14:45 1m bar's down-close. That entry is ~30620 (the owner's is 30635.75) with RR(T1) 1.3. The key is configurable.

Why condition (d): on the same day the 13:10 5m bar spiked through the whole band to 30694 and CLOSED above the 0.786 (30691.75). Without (d), a 13:18 re-raid of 30640 armed. Its "OB" was the 127-point spike bar and the stop was 30695. The trade (q=1) would have pre-empted the owner's 14:53 trade, because legacy stays IN_TRADE. That retrace had already left the OTE band, so (d) sends it to POST_SWEEP.

  - **Root cause (pre-existing, Agent 03's file, not changed here):** `LevelEngine.levels` is a `ConcurrentHashMap<LevelType, KnownLevel>`. Enum keys hash by IDENTITY hash, so level iteration order, and with it raid-detection order and `RaidDetector.getRecentRaid` tie-breaks, depends on the JVM's identity-hash sequence. Any extra allocation earlier in the run shifts it.
  - Proof: `git stash` → base run = Main exactly (reproduced twice). The same code with only extra allocations → this tie flips.
  - **Hand-off:** use `new EnumMap<>(LevelType.class)` (or a deterministic tie-break on level significance / price) in `LevelEngine` / `RaidDetector`.
