## 1. THE FOUR STARVATIONS AND THE FIXES

### S-1: no re-arm after a position closes (legacy target model, the default)

**Defect.** `processLegacyRearm` handled only INVALIDATED. A PositionClosedEvent for an EXECUTED trade cleared the latch but left the machine IN_TRADE until the core's "expired (200 bars without progress)". On 09-28 the 12:32 short was flat at 13:08, and the machine sat IN_TRADE until 15:38. It therefore missed the 14:53 G1 short.

**Fix (`StdvOteRunnerStrategy`).**
- A PositionClosedEvent that arrives while the machine is IN_TRADE with `executedSinceEmit` sets `closedAwaitingRearm` and starts `setup.rearmCooldownBars`.
- When the cooldown runs out, `rearm()` runs under the unchanged `canRearm`. That means no open position (both the event latch and the account map), the frequency limits (`maxTradesPerDay`, `maxConsecutiveLosses`), and NO_ENTRY/WEEKEND (SCORING) or an open killzone (BLOCKING).
- Scalp mode (`processScalpRearm`) already worked this way. It now also honours the flag.
- Signals that never executed keep the Agent 05 path ("signal not executed (released)" → invalidate → re-arm).

**New key.** `setup.rearmAfterClose` (BOOL, default `true`) is registered in `EngineConfig.KEYS`, set in `engine-defaults.properties`, read by `SessionConfig.rearmAfterClose()` and printed on a new boot line, `LIFECYCLE (Agent 05.3)`. Setting it to `false` restores the one-trade-per-window discipline: IN_TRADE stays terminal after an executed trade. This is kept for A/B.

### S-2: resting orders outlive their setup

**Defect.** On 09-24 the 14:03 LONG `e=30607` (3 micros) never filled. Its setup died at 15:07 ("expired (200 bars)"), but `orders=1` persisted until the SIM TTL.

**Fix.**
- **New event.** A new `event/SetupCancelledEvent` (`EventType.SETUP_CANCELLED`, mapped in `EventBus`).
- **Strategy.** `StdvOteRunnerStrategy.endEmittedSetup` publishes the event when the setup that emitted a signal ends without an executed position. The setup can end in three ways:
  - it leaves IN_TRADE for any reason (invalidated, expired, bias flip, entry timeout, …); this is checked at the end of every candle;
  - it is re-armed; `rearm()` calls `endEmittedSetup("re-armed")` first;
  - the same hook runs for the duplicate-bias fast re-arm (the second trigger covers it).

  The strategy releases its own latch at the same moment (`positionOpen=false`), so no synthetic PositionClosedEvent follows. An executed setup publishes nothing, because it has no resting entry.
- **SIM.** `ExecutionEngine` subscribes in `setEventBus`, but acts only when `simulationEnabled`. `cancelEntryForSetup` removes every unfilled entry order for the symbol and publishes one `GateDecisionEvent(gate="ORDER", reason="ORDER: cancelled — setup <reason>")` per order. It never touches a partially filled order, a position, or another symbol.
- **LIVE.** `LiveEngineRunner.handleSetupCancelled` calls `connector.cancelOrder(id)` and `removeOrderById`, then publishes the same GateDecisionEvent. It remembers the id, so the broker's CANCELED callback does not publish a second latch release, which could otherwise invalidate the NEXT setup. If the cancel fails, the order TTL remains the backstop and the failure is logged.
- **Backstop.** `order.ttlBars` is unchanged.

### S-3: partial exits are not counted as completed trades

**Defect.** `executePartialClose` booked P&L and reduced the position. It never created a Trade, never called `recordTradeCompleted`, and never published a PositionClosedEvent.
- A position flattened by partials (09-28 12:32, 1 micro, closed by the 1R partial at 13:08) produced no Trade, and `closedTrades` stayed 3.
- It was never counted for `maxTradesPerDay` or `maxConsecutiveLosses`, so the frequency gates missed it.
- A partial followed by a stop produced a Trade holding only the final leg (for example `q=2 pnl=17.00`).
- `riskAmount` was never set, so R printed `0.00`.

**Fix (`ExecutionEngine`).**
- **Ledger.** `executeFill` opens a per-symbol `PositionLedger` (side, entry, filled qty, initial risk). Initial risk is |entry − ORIGINAL stop| / tick × tick value × qty.
- **Legs.** Every exit leg joins the ledger, whether it is a partial, the stop, the target or the flatten.
- **Flat.** When the position goes flat, through `closePosition` or through a partial that flattens it, `completeTrade` records **exactly one** Trade:
  - qty = contracts exited;
  - exit = VWAP of the legs;
  - P&L = sum of the legs;
  - `riskAmount` = the initial $ risk, so R = P&L / initial risk;
  - notes list the legs.
- **Once per position.** `completeTrade` calls `accountState.recordTradeCompleted(total)` once, notifies the listener once, and publishes one PositionClosedEvent with the total P&L.
- **Realized P&L.** Still booked per leg, exactly as before, and never booked twice.
- **LIVE journaling.** Bracket partial legs go to `recordExternalPartial`. The stop, or a final TP with an unbooked remainder, merges them through `recordExternalTrade`. When every TP level was a partial, `finalizeExternalTrade` does the merge. The result is one journaled Trade per position. LIVE `AccountState` accounting is unchanged.

### S-4: LevelEngine iteration order is non-deterministic

**Defect.** `LevelEngine.levels` was a `ConcurrentHashMap<LevelType, KnownLevel>`. Enum keys hash by identity, so iteration order changed with unrelated allocations. That order feeds raid detection, raid listeners and `scoreSweep` tie-breaks. On 09-24 at 12:16, two same-bar, score-9 raids ("NY PM Session Low 30671.25" and "Asia Session Low 30642.75") flipped between runs. See §4: on Main, two consecutive cfg A runs gave different md5s.

**Fix.**
- **LevelEngine.** Now uses `ConcurrentSkipListMap<LevelType, …>`. It is thread-safe like before, and it iterates in LevelType ordinal order, the same order as an EnumMap.
- **RaidDetector.**
  - `activeRaids` and `recentRaids` are skip-list maps keyed by raid id.
  - There is ONE comparator, `BEST_RAID_ORDER`: higher score, then fewer bars since the raid, then the later raid time, then the higher swept price, then the id. `getBestRaidForEntry`, `getRaidByDirection` and the tie-break inside `getRecentRaid` all use it; `getRecentRaid` still sorts by recency first, as documented.
  - `scoreSweep` breaks significance ties by the higher price.

**Harness determinism (Fable's `FunnelAutopsyHarness`, test code only).** The harness drives the real asynchronous `EventBus`. It now calls a new `EventBus.awaitIdle()` after each step, meaning after `exec.onNewCandle`, after `runner.onCandle` and after the risk/submit step.
- `awaitIdle` counts queued events plus unfinished handler tasks.
- Production code never calls it.
- It models a live minute bar, where every handler finishes long before the next candle.

Without it, the timing of the PositionClosedEvent handler varied between runs: the cfg B 01:34 close re-armed at 01:42 on Main, against 01:40 once the handlers are awaited.

The harness also gets three more changes:
- It counts fills from the `ExecutionListener`. A fill and a stop inside one bar used to show `fills=0`, which was hand-off #4 of A-05.2.
- It logs `ORDER` / `ORDER_TTL` / `FLATTEN` gate events.
- It prints FILL / CLOSED / ORDER / RE-ARMED lines in the transcript.
