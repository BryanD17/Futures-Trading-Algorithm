## 0. The defect, and its real root cause

```
11:44:17.006 Order 3582761728 FILLED: MNQ 2 @ 30630.75           (TP1)
  Remaining: 3 contracts
[BRACKET] MOVING STOP TO BREAKEVEN: MNQ   New Stop: 30647.0
11:44:17.010 Cancelling order: 3582761719
11:44:17.077 Order cancelled successfully: 3582761719            <- broker DID cancel the stop
[BRACKET] ERROR cancel of working stop 3582761719 failed (breakeven move): Order quantity must be positive, got: 0
            — old stop kept working, no replacement placed          <- FALSE
[BRACKET] Updating stop quantity to 3 for MNQ
[BRACKET] ERROR cancel ... rejected by TopstepX: null (code: 5) — old stop kept working   <- FALSE
11:44:19.002 Order 3582761719 CANCELLED
```

The brief reported that the remaining-quantity bookkeeping read 0. **The log shows otherwise:** the counter was 3 ("Remaining: 3", "Updating stop quantity to 3"). The exception `Order quantity must be positive, got: 0` came from **inside `TopstepConnector.cancelOrder`**. After the broker returned `success:true` and the connector logged "Order cancelled successfully", the connector built a placeholder `Order` with `.quantity(0)` to notify the order listener. `Order`'s builder rejects 0 (`domain/Order.java:35`), so the exception escaped `cancelOrder`. BracketOrderManager caught it in its cancel `try`, concluded the cancel had failed, and returned without placing the replacement. The second path ("Updating stop quantity") then got code 5 because the order was already cancelled, and it logged the same false claim.

The fix removes both the trigger (the connector) and the fragile design around it (the manager). The brief's items 1-6 are all implemented. Item 1, quantity from the position, is defence in depth: the counter was not the root cause.

## 1. The fix

| # | requirement | implementation |
|---|---|---|
| root | connector turned a confirmed cancel into an exception | `cancelOrder`: the placeholder Order uses the tracked order's symbol/side/qty (never 0), and the listener call is wrapped. A notification can no longer turn a broker-confirmed cancel into a failure. |
| 1 | quantity from the POSITION | `setPositionQuantityProvider(sym -> abs(accountState.getPosition(sym).getQuantity()))`, wired in LiveEngineRunner. The runner updates the Position in `onPartialTakeProfitFilled`, which runs before the stop operation. Fallback is the TP ledger (total - filled TPs), not a decrementing counter. `replaceStop` / `submitStopWithRetry` refuse qty <= 0 and never cancel anything in that case. A partial fill now runs **one** stop operation: a breakeven move at the position size, or a resize. The old code ran two back-to-back cancel/replaces. |
| 2 | place-then-cancel | `replaceStop` **Phase A** places the new stop (3 attempts, backoff 150/300 ms). Only after TopstepX returns an order id does it cancel the old stop (3 attempts). **Phase B** runs if the new stop cannot be placed alongside the old one (e.g. TopstepX refuses a 2nd stop): cancel-then-place. It retries the new level 3x, then the old level 3x, then **FLATTENs** at market via the connector and publishes GateDecisionEvent `BRACKET: stop lost — flattened (<why>)`. If Phase B's cancel fails and the broker (queried) still shows the old stop, nothing is placed and the log says so; the old stop is verified working. |
| 3 | broker-verified | New `TopstepConnector.fetchBrokerSnapshot()` = `POST /Position/searchOpen` + `POST /Order/searchOpen`. It returns `BrokerPosition` / `BrokerOrder` records (contract id mapped back to the engine symbol). Every stop operation ends in `verifyAtBroker`, which logs `BROKER VIEW <sym> after <op>: position ..., working stops [...]` and enforces exactly **one** stop with size == broker position size (see the table in section 3). If the broker view is unavailable, that is logged; it is never assumed. |
| 3 | periodic reconciliation | `reconcileWithBroker()` is scheduled every 30 s in LiveEngineRunner. It covers a position with no stop (the LIVE end state), a size mismatch, extra stops, a stale engine belief, a broker flat on 2 consecutive passes, and untracked positions (section 3). |
| 4 | code 5 = already gone | `cancelOrder` throws `TopstepConnector.OrderNotWorkingException` for cancel codes 5 and 2. The manager maps it to `CancelResult.NOT_WORKING` and logs "was NOT open at TopstepX (code 5) — already cancelled or filled; nothing left to cancel". Note: ProjectX's published enum may name 5 differently. Code 5 was observed LIVE on an already-cancelled order, and the manager confirms state with `searchOpen` after every operation, so a wrong guess is caught. |
| 5 | flat → cancel all | `sweepSymbolOrders` runs after the final TP, a stop fill, a legacy TP fill, the unprotected-flatten fill, and a broker-flat reconciliation. It cancels **every** working order for the symbol, then re-queries to verify an empty book (ERROR + event if not). It refuses to strip orders if the broker still shows a position. Separately, the "all TPs filled" test now uses the position/ledger. Before, a TP that failed to submit could make the manager cancel the stop while contracts were still open. |
| 6 | restart | Chosen behaviour: **adopt**. `reconcileOnStartup()` runs right after `eventBus.start()`, before any signal can trade. Each untracked broker position is logged loudly (`!!! UNTRACKED BROKER POSITION`) and published as an event, then wrapped in an `adopted` bracket. If a broker stop exists, it is adopted and fill-tracked via `trackExistingOrder`, with its size enforced. Otherwise a stop is placed at **breakeven** (the broker average price, tick-aligned). If that is rejected (e.g. price already through it), the position is FLATTENED. `onPositionAdopted` registers the Position in `accountState`, so the entry gates see the symbol as in-position (no second entry) and its exit books P&L. A later engine bracket for the symbol supersedes an adopted one: the adopted stop is cancelled after the new stop is acknowledged. |

## 2. Log-text corrections (every broker-state claim now follows a broker response)

| before | after |
|---|---|
| `ERROR cancel of working stop X failed (...): <e> — old stop kept working, no replacement placed` (printed on ANY exception, including the post-cancel listener crash) | Removed. Replaced by: `Order X cancelled (TopstepX acknowledged)`, `Order X was NOT open at TopstepX (code 5) — already cancelled or filled; nothing left to cancel`, or `ERROR cancel of order X FAILED: <e> — its state at the broker is UNVERIFIED`. The Phase-B follow-up is `stop X is still WORKING at the broker (verified)` or `broker state UNKNOWN (query failed)`, and each is printed only after a `searchOpen` query. |
| `✓ Stop Loss submitted: id` / `✓ TPn submitted` / `✓ Take Profit submitted` | `... acknowledged by TopstepX: id` (printed only when the order/place response carried an order id) |
| `✓ New breakeven stop submitted: id` | `New stop id acknowledged by TopstepX: BUY STOP 3 @ 30647.0 (breakeven move)` + `✓ Breakeven stop working: id (3 @ 30647.0, TopstepX acknowledged)` + `BROKER VIEW ...` |
| `✓ Stop updated: id (qty: n)` | `✓ Stop updated: id (qty: n, TopstepX acknowledged)` + `BROKER VIEW ...` |
| `ERROR Failed to move stop to breakeven` (no state) | `ERROR breakeven move failed — position was flattened` or `— working stop is id @ px (see BROKER VIEW)` |
| `[BRACKET] ✓ Order X canceled` (generic helper, printed even when TopstepX answered "not open") | `cancelAtBroker` returns CANCELLED / NOT_WORKING / FAILED, each with its own truthful line |
| `❌ ERROR Failed to submit TPn — stop stays working (position protected)` | `... — stop <id> (acknowledged) protects the position` |
| (none) | `BROKER VIEW <sym> after <op>: position ..., working stops [...] — OK (1 stop, size n == position n)` after every stop operation, plus `FLAT, 0 working orders (verified; k cancelled)` after every flat |

## 3. Reconciliation matrix (`enforceProtection`)

| broker shows | action |
|---|---|
| position, 0 stops | ERROR + event `BRACKET: broker position without a stop — re-placing`. Places a stop at `targetStopPrice` (the breakeven price once a move was requested, even if that move failed), else the current stop price, at the broker position size. Retries, then the old level, then flatten. |
| position, 1 stop, size ≠ position | place-then-cancel resize to the position size |
| position, >1 stops | keep the engine's tracked stop, cancel the extras (an over-covering stop can reverse the position) |
| position, stop id ≠ engine belief | adopt the broker's stop, fill-tracked (the LIVE case: engine believes 3582761719, broker has Fable's 3582792632) |
| flat, bracket tracked (2 passes) | ERROR + event, drop the bracket, sweep the symbol's orders |
| untracked position | adopt (immediately at startup; on the 2nd consecutive periodic pass, since one pass could be an entry fill still in flight) |
| query failed | log, infer nothing, touch nothing |

## 5. Notes for Fable / deployment

- The running engine (:8080) still has the old code and still believes stop 3582761719 is working. The fix takes effect only on restart. On restart, `reconcileOnStartup` would find the SHORT 3 and adopt Fable's manual stop 3582792632 (BUY STOP 3 @ 30647.50) with no duplicate. If the position is flat by then, nothing happens.
- **Conflict risk with the broker-side watchdog:** reconciliation cancels stops beyond one per position. If the watchdog places its own stop while the engine's stop is working, the engine will cancel the extra every 30 s. Stop the watchdog once the patched engine is confirmed managing the position.
- A tracked bracket whose broker position disappears without a fill callback is dropped after 2 passes. The engine `accountState` position is **not** cleared (no P&L is invented), so the symbol stays blocked for new entries until restart. This is conservative by design.
- ProjectX endpoints used: `/Order/searchOpen`, `/Position/searchOpen` (body `{accountId}`), `/Order/cancel`, `/Order/place`. PositionType 1=Long/2=Short; order status 1=Open/6=Pending are treated as working. These were not exercised against the real API from this worktree (no LIVE calls were made); the first LIVE restart log will show the `BROKER VIEW` lines to confirm them.
